# Sriyanth: learned evaluator (value network)

## Scope and interfaces

Sriyanth's modules are `c4/nn/model.py`, `c4/nn/train.py`, `c4/nn/evaluator.py`
and `c4/nn/saliency.py`, with their tests (`tests/test_nn.py`, 14 tests). They
train a convolutional network on the self-play data from Veer's pipeline
(section 3, `c4/selfplay/`) and plug it into Shridali's search through the same
`Evaluator` interface as Rujuta's hand-written heuristic. The network never
chooses a move. It only answers "how good is this board for the player to
move?" at the search's depth limit, so the search, the trace and the
explanations work the same whichever evaluator is used. No teammate files were
changed.

## Network

Input is the 3 x 6 x 7 tensor from `c4.selfplay.dataset.encode`: the stones of
the player to move, the opponent's stones, and the cells that can be played
next. The same function is used in training and at play time, so the layout
always matches.

| Layer | Details |
|---|---|
| 4 x convolution | 3 x 3, 64 filters, padding 1, batch norm, ReLU (board stays 6 x 7) |
| 1 x convolution | 1 x 1, 8 filters, batch norm, ReLU |
| Fully connected | 8 x 6 x 7 = 336 -> 128, ReLU |
| Output | 128 -> 1, tanh, value in (-1, 1) for the player to move |

The network has **156,889 parameters**. The proposal (4.2) describes four 3 x 3
convolutional layers followed by a 128-unit layer and about 150k parameters.
Built exactly like that, the 128-unit layer alone would have 64 x 42 x 128 =
344k parameters (about 457k in total). The extra 1 x 1 layer reduces 64
channels to 8 before that layer, which keeps the network at the size the
proposal gives and fast enough on a CPU.

## Training

- **Labels.** Every position is labelled with the final result of its game for
  the player to move: +1 win, 0 draw, -1 loss (Veer's labels, section 3).
- **Split by game.** `split_by_game` first holds out 10% of games as the test
  set, which is used only for the final numbers. A further 10% of the remaining
  games form a validation set for choosing the epoch, and the rest are for
  training. With the strict split, any position (or its mirror image) that also
  occurs in a training game is removed from validation and test, so both are
  truly unseen.
- **Mirroring.** In each batch a random half of the boards is flipped left to
  right, which is the same as training on the mirrored data set.
- **Optimiser.** Mean squared error, Adam (learning rate 0.001, weight decay
  0.0001), batch size 512, on a CPU.
- **Early stopping.** The weights with the lowest validation error are kept.
  Training stops when validation error has not improved for 3 epochs (limit 15
  epochs or a time budget).

Two rounds were trained (proposal 4.2):

| | Round 1 network | Round 2 network |
|---|---|---|
| Training data | round 1 (20,000 games, heuristic self-play) | rounds 1 and 2 (25,000 games) |
| Starting weights | random | round 1 network |
| Training positions (before mirroring) | 513,345 | 634,915 |
| Epochs run (best epoch) | 7 (4) | 4 (1) |
| Training time | 7.2 min | 4.9 min |
| Test positions | 16,121 | 21,493 |
| **Test MSE** (constant-guess baseline) | **0.663** (0.910) | **0.586** (0.882) |
| **Winner predicted correctly** | **75.3%** | **77.2%** |

Winner accuracy counts unseen test positions whose game was won or lost, and
checks whether the sign of the network's output names the right player. Both
networks clearly beat the constant guess (always predicting the average
result): the round 2 network's error is 34% lower. The two test sets are not
identical (the round 2 set also contains round 2 games), so the step from round
1 to round 2 is an improvement on similar data, not an exact comparison. Veer's
section reports that the round 1 network got only 64.3% of round 2 positions
right before retraining, which is why training in rounds helps.

The training curves are in `results/training/round1.json` and `round2.json`
(figure: `results/plots/training_round*.png`). Training error keeps falling
(round 1: 0.58 to 0.38) while validation error levels off near 0.67 after epoch
2, so the network starts to fit its training games rather than general
patterns. Early stopping keeps the best epoch, not the last one.

**Round 1 data settings** (generated by Sriyanth with Veer's `generate.py`):
heuristic evaluator, depth 4, 2 to 8 random opening moves, epsilon 0, seed 0,
500 games per shard, 10 worker processes. It took 15.1 minutes (about 22 games
per second) and stored 634,661 positions. Results: first player 10,875 wins,
second player 7,745, draws 1,380.

## Plugging the network into the search

`NNEvaluator` (`c4/nn/evaluator.py`) follows the `Evaluator` protocol, so it is
a drop-in replacement for the heuristic. `NNEvaluator()` loads
`models/nn_latest.pt` (used by the web interface), and `NNEvaluator.load(path)`
loads a given file (used by self-play round 2).

- **Score scale.** The tanh output v is turned into the search's integer score
  as round(1000 v) (`NN_SCALE` in `c4/trace.py`), so it stays far below the
  scores for a proven win or loss (100,000 minus plies). The search always
  prefers a forced win to a position the network merely likes.
- **Caching.** Every value is cached by the board's key, because the same
  positions come up many times inside one search.
- **Batching.** `evaluate_batch` scores many boards in one forward pass. The
  search currently calls the evaluator one board at a time, so this is
  available but not used during play.
- **Speed.** One network evaluation takes about 315 microseconds against about
  19 for the heuristic (Veer's measurement during review), roughly 16 times
  slower. At the same time per move the network search therefore reaches less
  depth. The playing-strength comparison (section 6) is done at equal time per
  move, as the proposal requires, so this cost is included.

## Saliency for quiet moves

For moves where no tactical rule fires, the explanation falls back on the
network (Naman's section 4). `c4/nn/saliency.py` uses occlusion (Zeiler and
Fergus): each stone is removed in turn, the network scores the board again, and
the change in value is that stone's importance. All the occluded boards go
through the network in one batch (at most 43 boards).

- `saliency_map(board, evaluator)` returns a 6 x 7 array for the player to move
  (positive: the stone helps that player), for the interface overlay.
- `move_saliency(board, col, evaluator, k=3)` returns the network's value after
  the move and the k most important stones, each with its owner ("mover" or
  "opponent") and its effect, from the point of view of the player who moved.
  The explanation layer phrases these as "the stones at ... made this position
  look good".

A stone is removed from the input planes rather than from the board, so
removing one from the middle of a column leaves the stones above it "floating".
The network still gives a value, which is fine for measuring importance, but
those boards could not occur in a real game.

## Limitations

- **Noisy labels.** A position is labelled with how its game actually ended
  between imperfect players, so a won position that was later thrown away is
  labelled as a loss. This limits the accuracy any network can reach against
  these labels. The solver-agreement check (section 6) measures against perfect
  answers instead.
- **Mild overfitting.** Validation error stops improving after a few epochs
  while training error keeps falling. More and more varied self-play data would
  help more than longer training.
- **Less data than planned.** 25,000 games against the proposal's 50,000.
- **Speed.** The network is about 16 times slower per evaluation, so it searches
  less deeply at equal time. Using `evaluate_batch` inside the search, or the
  network only near the root, are the obvious next steps.
- **Tromp's data set not used.** `train.py --tromp` can report accuracy on
  Tromp's UCI positions as an extra test set, but this was not run for the
  report.
- **Architecture.** Five convolutional layers instead of the four in the
  proposal (see Network above).

## Reproducing

From the repository root:

```bash
python -m c4.selfplay.generate --games 20000 --round 1 --workers 10
python -m c4.nn.train --data data/selfplay/round_1 --out models/round1.pt --max-minutes 40
python -m c4.nn.train --data data/selfplay/round_1 data/selfplay/round_2 \
       --init models/round1.pt --out models/round2.pt --max-minutes 30
pytest -q tests/test_nn.py
```

Training writes `models/<name>.pt`, copies it to `models/nn_latest.pt`, and
writes the curves to `results/training/<name>.json`. Model weights and self-play
data are git-ignored; the round 2 network (`nn_latest.pt`, about 600 KB) was
shared with the team directly.
