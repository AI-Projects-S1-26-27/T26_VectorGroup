# Veer: self-play data pipeline

## Scope and interfaces

Veer's modules are `c4/selfplay/generate.py` and `c4/selfplay/dataset.py`, with
their tests (`tests/test_selfplay_generate.py`, `tests/test_selfplay_dataset.py`,
20 tests). They produce the training data for Sriyanth's value network
(section 3) and turn it into tensors for `c4/nn/train.py`. They use Shridali's
board and search (`c4/board.py`, `c4/search.py`) and, when present, Rujuta's
evaluator, transposition table and move ordering. No teammate files were changed.

## How one self-play game is generated

1. **Random opening.** Each game starts with 2 to 8 random legal moves (the
   number is chosen per game), so games start from many different positions.
2. **Search for every other move.** After the opening, every move is chosen by
   the real search at a fixed depth (4 plies by default) with the chosen
   evaluator: the hand-written heuristic for round 1, the previous network for
   later rounds. If several moves share the best score, one of them is picked at
   random, which adds variety without weakening play. An optional `--epsilon`
   adds occasional random moves later in the game; it was 0 for both rounds.
3. **Labelling.** When the game ends, every position in it is labelled from the
   point of view of the player to move there: +1 if that player went on to win,
   -1 if they lost, 0 for a draw. This matches the network's tanh output and the
   viewpoint of scores in `c4/trace.py`. Finished positions are not stored,
   because the evaluator is never asked about them.

Every game has its own seed (derived from the round, the game index and a base
seed), so with a fixed depth the same command always produces the same data,
whatever the number of worker processes. Games are written in shards of a few
hundred games (`data/selfplay/round_N/shard_*.npz`, git-ignored) with a
`meta.json` recording the settings and totals. A run can be stopped and
restarted with the same command: finished shards are skipped. A round folder
refuses data made with different settings unless `--force` is given.

Each stored row holds the position and mask bitboards, the label, a game id
(unique across rounds), the number of stones, the move played, its search
score, and whether that move was random.

## From shards to training data

- **Network input** (proposal 4.2): a 3 x 6 x 7 tensor with the stones of the
  player to move, the opponent's stones, and the cells that can be played next.
  `encode(board)` is shared by training and by the network evaluator at play
  time, so the network always sees the same layout.
- **Split by game, not by position** (proposal 4.2): whole games go to train or
  test. With `strict=True` (the default) a test position is also dropped if the
  same position, or its mirror image, appears in any training game. Openings
  repeat across many games, so without this the test set would contain
  positions the network had already trained on.
- **Mirroring:** Connect-4 is left-right symmetric, so every training position
  can also be used flipped. `train.py` mirrors a random half of each batch,
  which is equivalent to doubling the data without storing it twice.

## Dataset handoff and results

| | Round 1 | Round 2 |
|---|---|---|
| Played with | Hand-written heuristic | Round 1 network (`models/round1.pt`) |
| Generated by | Sriyanth, using `generate.py` | Veer, using `generate.py` |
| Games | 20,000 | 5,000 |
| Positions stored | not recorded in the repo | 149,181 (298,362 with mirroring) |
| Results (first player / second / draw) | not recorded in the repo | 2,631 / 1,964 / 405 |
| Settings | not recorded in the repo | depth 4, 2 to 8 random opening moves, epsilon 0, seed 0 |

**Handoff confirmation.** Round 2 was generated on 16 November 2026 (about
70 minutes on 2 CPU cores) and handed to Sriyanth as the
`data/selfplay/round_2` folder. Before handoff every one of the 5,000 games was
replayed from its stored moves: all were legal, every stored position matched
the replay, and every label matched the game's real result. The round 1 network
was also confirmed to load and play through `--evaluator network`, and
`train.py --init models/round1.pt` was confirmed to accept the new data.
Sriyanth's `results/training/round2.json` lists both `data/selfplay/round_1`
and `data/selfplay/round_2` (25,000 games), confirming both rounds were used.

**Effect on the network** (from Sriyanth's training results; winner accuracy is
measured on unseen test positions whose game was won or lost):

| | Round 1 network | Round 2 network |
|---|---|---|
| Training data | round 1 | rounds 1 and 2, starting from the round 1 network |
| Training positions (before mirroring) | 513,345 | 634,915 |
| Test MSE (constant-guess baseline) | 0.663 (0.910) | 0.586 (0.882) |
| Winner predicted correctly | 75.3% | 77.2% |

On the round 2 positions themselves, the round 1 network predicted the winner
correctly only 64.3% of the time (MSE 0.856). Positions from the network's own
games were harder for it than round 1 positions, which is the reason the
proposal trains in rounds. After retraining on them, test accuracy rose by about
two points and the test error fell from 0.663 to 0.586.

## Limitations

- **Fewer games than planned.** The proposal aimed for at least 50,000 games and
  roughly a million positions after mirroring. Rounds 1 and 2 give 25,000 games;
  their 634,915 training positions reach about 1.27 million with mirroring, but
  the game count is half the target.
- **Repetitive round 2.** Only 75,821 of the 149,181 round 2 positions are
  unique (73,585 up to mirroring). The network almost never scores two moves
  exactly equal, so after the random opening many games follow the same lines.
  A further round should use `--epsilon 0.05` for more variety.
- **Noisy labels.** A position is labelled with how its game ended, and the games
  were played by an imperfect engine, so a winning position later thrown away by
  a blunder is labelled as a loss. This caps the accuracy any network can reach
  against these labels; the solver-agreement test (section 6) measures against
  perfect answers instead.
- **Speed.** At depth 4 a game takes about a quarter of a second per CPU core with
  the heuristic, but about two seconds with the network, so network rounds take
  several times longer to generate.

## Reproducing

From the repository root:

```bash
python -m c4.selfplay.generate --games 5000 --round 2 --evaluator network --model models/round1.pt --workers 2 --games-per-shard 250
python -m c4.selfplay.dataset data/selfplay/round_2      # the summary numbers above
pytest -q tests/test_selfplay_generate.py tests/test_selfplay_dataset.py
```

Round 1 used the heuristic evaluator (`--evaluator heuristic --round 1`); its
other settings are in Sriyanth's `data/selfplay/round_1/meta.json`, which is not
in the repository.
